# Results: full and stress profiles, Windows 11, Intel Core i5-9400F (2026-11-25)

These are the results of the `full` and `stress` profiles: every scenario, library and size the suite plans. All of them ran
on one developer desktop that was not isolated, so treat them as informational. Read [methodology](../methodology.md) and
[interpreting results](../interpreting-results.md) before drawing conclusions. UnlimitedPDF is the baseline that ratios
are calculated against. It is not a presumed winner.

**How to read the numbers.**

- **Time ratio** is the competitor's mean divided by UnlimitedPDF's mean, for the same scenario and parameters. Above 1
  means the competitor took longer, and below 1 means it was faster.
- **Allocated** is cumulative managed allocation per operation. It is not live, peak or native memory. SkiaSharp does
  most of its work in native code, so its managed allocation is low by construction.
- A ratio exists only where UnlimitedPDF passed. Unsupported cases are listed, never ranked.

Every number below comes from the run folders listed next. The per-case tables in the appendices were generated directly
from those folders' `results.json` and `profiler/results.json`.

## Runs used

The suite was run twice. The first pair of runs found a fixture defect: a few randomly generated text lines were wider
than the page. On those lines, PDFsharp, PdfPig and UnlimitedPDF kept the off-page glyphs in the content stream, while
SkiaSharp dropped them. Three SkiaSharp stress cases therefore failed text validation:

- coloured rich text, 500 pages
- rich text, 500 pages
- plain text, 5,000 pages

Fixture version 2026.11.2 caps every positioned line at a width measured from the Noto fonts, and an integration test
now checks every line (see [methodology](../methodology.md#principles)). Only the categories that draw those lines were
re-run: Generation and FileOutput, plus the resource profiler. The other categories' inputs did not change. Tables,
business documents, multilingual text, HTML and the manipulation input PDFs are generated by code that the fix did not
alter. The fix did not change the 2-argument `Words.Sentence` overload either, because it still draws the same random
values. Those categories are therefore taken from the first runs.

## Findings

### Positioned generation (Generation category)

- **Empty pages.** UnlimitedPDF is fastest: 7.51 µs for one page. The others take 1.25× to 3.13× as long, and 1.24× to
  2.74× at 10 pages.
- **Plain text with an embedded Noto font**
  - From 10 pages up, every competitor is faster. PDFsharp is 0.05× to 0.07× (roughly 15 to 20 times faster), PdfPig 0.22× to 0.48×
    and SkiaSharp 0.23× to 0.54×.
  - At 1 page, UnlimitedPDF (5.41 ms) is faster than PdfPig (2.50×) and SkiaSharp (3.09×), but slower than PDFsharp (0.22×).
  - UnlimitedPDF's cost grows by about 4.8 ms and 4.6 MB of managed allocation per page: 4.84 s and 4.55 GB at 1,000 pages,
    against 235 ms and 175 MB for PDFsharp.
  - At 5,000 pages (stress), UnlimitedPDF takes 24.3 s, and PDFsharp 1.23 s (0.05×), PdfPig 5.17 s (0.21×), SkiaSharp
    5.54 s (0.23×).
- **Plain text with the standard Helvetica font** (UnlimitedPDF and PdfPig only)
  - UnlimitedPDF writes 1,000 pages in 77.7 ms. PdfPig is 59× to 120× slower.
  - UnlimitedPDF's standard-font path is about 62 times faster than its own embedded-font path at 1,000 pages (77.7 ms
    against 4.84 s). The embedded-font cost, not text layout as such, accounts for most of the time above.
- **Output size.** UnlimitedPDF writes its page content streams uncompressed: the 1-page sample has 45 readable `BT`
  operators and a single Flate-compressed stream. PDFsharp, PdfPig and SkiaSharp compress their content streams. Version
  1.1.0 has no public compression option. UnlimitedPDF's embedded-text output is therefore about 23 KB per page, against
  1.3 KB per page for PDFsharp at 1,000 pages: 22.8 MB against 1.27 MB.
  SkiaSharp's outputs start large (313 KB for one page), because the 4.157.0 build embeds large font programs.
- **Rich text** (three faces and several sizes)
  - At 1 page, PDFsharp is 0.52×, PdfPig 7.62× and SkiaSharp 8.82×.
  - At 100 pages, PDFsharp is 0.06×, PdfPig 0.33× and SkiaSharp 0.32×.
  - At 500 pages (stress), PDFsharp is 0.09×, PdfPig 0.26× and SkiaSharp 0.22×.
- **Images**
  - **PNG:** UnlimitedPDF is fastest at every size, with the others at 6.17× to 15.7×. PNG pixels must be re-encoded, and
    PdfPig and SkiaSharp take longer than PDFsharp at 1 image.
  - **JPEG:** UnlimitedPDF leads at 1 image (others 1.47× to 26.2×) and at 10 images (1.04× to 10.5×). At 100 images
    PDFsharp is faster (0.77×), and PdfPig (1.51×) and SkiaSharp (1.98×) are slower.
  - **500 JPEG images (stress):** UnlimitedPDF takes 121 ms and is the slowest. The others are 0.46× to 0.62×.
- **Mixed text, image and shapes**
  - At 1 page, PDFsharp is faster (0.41×), and PdfPig (4.34×) and SkiaSharp (5.73×) are slower.
  - From 10 pages up, every competitor is faster, at 0.10× to 0.91×. At 1,000 pages (stress) the range is 0.19× to 0.27×.
- **Coloured rich text and vector graphics** have no UnlimitedPDF case, because 1.1.0 has no text-colour, line, stroke or
  curve API. Absolute values for PDFsharp, PdfPig and SkiaSharp are in the appendix, without ratios.
  - Coloured text, 100 pages: PDFsharp 23.1 ms, PdfPig 127 ms, SkiaSharp 120 ms.
  - Vectors, 1,000 pages (stress): PDFsharp 441 ms, PdfPig 474 ms, SkiaSharp 814 ms.

### File output (FileOutput category)

Writing plain text to a file through each library's own file API follows the in-memory pattern. The ratios are 0.08×,
0.50× and 0.57× at 10 pages, and 0.05×, 0.25× and 0.27× at 100 pages, for PDFsharp, PdfPig and SkiaSharp. At 1,000 pages
(stress) they are 0.07×, 0.23× and 0.23×, where UnlimitedPDF takes 4.88 s. File I/O adds little: UnlimitedPDF takes
474 ms for 100 pages to a file, against 486 ms in memory.

### Layout: tables, images in tables, headers and footers (UnlimitedPDF and MigraDoc)

- **Simple table**
  - MigraDoc's time ratios are 1.30× at 10 rows, 0.88× at 100, 1.52× at 1,000, 2.32× at 10,000 and 28.4× at 100,000 rows.
  - MigraDoc's time grows faster than linearly: from 2.46 s at 10,000 rows to 302 s at 100,000 rows, 123 times longer for
    10 times the rows. UnlimitedPDF takes 1.06 s and 10.6 s.
  - Page counts differ, because UnlimitedPDF 1.1.0 has no table cell font-size setting and MigraDoc uses 10 pt. At 1,000
    rows UnlimitedPDF produces 28 pages to MigraDoc's 20, and at 100,000 rows 2,778 to 1,961.
  - UnlimitedPDF allocates about twice as much: 10.4 GB against 5.43 GB at 100,000 rows. Validation counts every row id,
    so both outputs contain the same rows.
- **Table with images.** MigraDoc's ratios are 2.40× at 10 rows, 2.99× at 100 and 2.15× at 1,000 rows (stress).
  MigraDoc's measured time includes the `base64:` encoding it needs for in-memory images.
- **Headers, footers and page numbers.** MigraDoc is faster at every size: 0.39× to 0.42×, and 0.38× at 5,000 pages
  (6.74 s against 17.7 s).
  - UnlimitedPDF also allocates more, at 3.21 GB against 1.36 GB for 1,000 pages.
  - Its output is about 10 times larger, at 16.4 MB against 1.68 MB, consistent with the uncompressed content streams.

### Business documents (UnlimitedPDF and MigraDoc)

- **All nine document kinds.** MigraDoc's ratios are 1.03× to 1.46×. Examples: invoice 3.60 ms against 4.45 ms, bank
  statement 43.2 ms against 57.1 ms, tabular report 210 ms against 306 ms.
- **Page counts differ** in two kinds, again because of the table layouts:
  - bank statement: 9 pages against 7
  - tabular report: 56 pages against 40

  On those two kinds UnlimitedPDF allocates more: 40.4 MB against 24.0 MB, and 210 MB against 111 MB.
- **Invoice batch.** 100 invoices take 353 ms against 423 ms (1.20×). 1,000 invoices (stress) take 3.66 s against 4.17 s
  (1.14×).

### Multilingual text (UnlimitedPDF and SkiaSharp with HarfBuzz; English also PDFsharp and PdfPig)

- **English**
  - PDFsharp is faster at every size: 0.42× at 1 page, 0.10× at 10 and 0.06× at 100.
  - PdfPig (4.77×) and SkiaSharp (6.31×) are slower at 1 page and faster at 100 pages (0.30× and 0.48×).
- **Complex scripts, SkiaSharp's ratios at 1 / 10 / 100 pages:**

  | Script | 1 page | 10 pages | 100 pages |
  |---|---:|---:|---:|
  | Hindi | 0.81× | 0.13× | 0.06× |
  | Telugu | 3.31× | 0.60× | 0.25× |
  | Tamil | 3.73× | 0.68× | 0.28× |
  | Mixed scripts | 1.14× | 0.18× | 0.10× |

- **Devanagari is the slowest script for UnlimitedPDF.** Hindi takes 2.88 s and 4.53 GB of managed allocation for
  100 pages, against 532 ms for Telugu and 429 ms for Tamil.
- **Text check only.** Extracted text must match exactly, but glyph-level shaping is not compared automatically. The
  PDFium renders in `samples/` are kept for visual inspection.

### Page manipulation (UnlimitedPDF, PDFsharp, PdfPig)

- **Merge.** UnlimitedPDF is fastest in all 12 cases, and also adds one bookmark per input file, which the others don't.
  - PDFsharp's ratios are 1.19× to 1.80×, and PdfPig's 1.82× to 77.6×. PdfPig is slowest on text-only inputs.
  - At 500 documents (stress), PDFsharp is 1.16× and PdfPig 3.33×.
- **Split into single pages.** PDFsharp's ratios are 1.53×, 1.61× and 1.10× for 10, 100 and 1,000 pages, but 0.60× at
  5,000 pages (stress), where PDFsharp is faster. PdfPig's ratios are 5.12× to 8.07×.
- **Split into page ranges.** PDFsharp's ratios are 1.05× to 1.61×, and PdfPig's 5.23× to 9.79×.
- **Extract pages.** PDFsharp is 0.90× on the small input and 1.15× on the large one. PdfPig is 4.39× and 1.39×.
- **Remove pages.** PDFsharp is faster, at 0.64× and 0.70×. PdfPig is 4.05× and 2.89×.
- **Reorder pages.** PDFsharp and UnlimitedPDF are level, at 1.02× and 0.99×. PdfPig is 6.77× and 3.15×.

### Resource profiler (`20261124-211354-full` and `20261124-221610-stress`)

The profiler runs each library in its own child process. Process memory values are never combined with managed
allocation.

- **Cold start** (median of 10 fresh processes each)

  | Workload | Library | Process start to first valid PDF |
  |---|---|---:|
  | 1-page text | SkiaSharp | 220 ms |
  | 1-page text | PDFsharp | 227 ms |
  | 1-page text | PdfPig | 270 ms |
  | 1-page text | UnlimitedPDF | 275 ms |
  | Invoice | UnlimitedPDF | 297 ms |
  | Invoice | MigraDoc | 348 ms |
  | Simple small HTML | UnlimitedPDF | 374 ms |

  - **Library initialisation**, which includes loading the fonts, takes about 40 ms for UnlimitedPDF and SkiaSharp, 6 to
    8 ms for PDFsharp and MigraDoc, and 2 ms for PdfPig.
  - **Outlier:** the first UnlimitedPDF process of the run took 730 ms, the first process after the build.
  - **Process exit:** PDFsharp and MigraDoc processes take longer to exit after writing the PDF. Their parent-observed
    lifetimes are about 695 and 822 ms, against 418 to 486 ms for the others. This was not investigated.
- **Sequential, warm, 10,000 documents of 1-page text**
  - Documents per second: PDFsharp 728, UnlimitedPDF 177, PdfPig 78, SkiaSharp 60.
  - Invoices: UnlimitedPDF 268 per second against MigraDoc's 220.
- **Concurrency**, with one adapter per worker on 6 cores. The table shows documents per second.

  | Workload | Library | 1 worker | 4 workers | 8 workers | 16 workers | 32 workers (stress) |
  |---|---|---:|---:|---:|---:|---:|
  | 1-page text | PDFsharp | 549 | 1,404 | 1,653 | 1,446 | 1,524 |
  | 1-page text | UnlimitedPDF | 164 | 388 | 386 | 408 | 465 |
  | 1-page text | SkiaSharp | 59 | 230 | 318 | 313 | 311 |
  | 1-page text | PdfPig | 78 | 87 | 97 | 106 | 111 |
  | Invoice | UnlimitedPDF | 236 | 464 | 451 | 448 | 559 |
  | Invoice | MigraDoc | 190 | 324 | 313 | 273 | 321 |

  - Above 6 workers the CPU is oversubscribed.
  - PdfPig's throughput barely rises with more workers, while its CPU use stays between 18% and 37%.
  - The stress profile's 16-worker runs process 10,000 documents rather than 2,000. They reach 524 text and 652 invoice
    documents per second for UnlimitedPDF, and 1,647 and 353 for PDFsharp and MigraDoc.
- **Process memory**
  - **PdfPig, 32 workers:** the peak working set reached 1,647 MB and the peak sampled managed heap 1,341 MB. The retained
    managed heap after two full collections was 1.6 MB, so the peak was transient.
  - **UnlimitedPDF's retained managed heap** grows with the worker count: 5.6 MB at 1 worker, 47 MB at 16 and 92 MB at 32,
    about 2.9 MB per worker. This is consistent with one adapter instance, and its fonts, per worker, kept until the run
    ends. It was not investigated further and is not described as a leak.
  - **Long-running, 10,000 documents on 1 worker:** no library showed growth. UnlimitedPDF retained 5.8 MB, PDFsharp
    5.2 MB, PdfPig 1.5 MB and SkiaSharp 3.4 MB.

## Limitations

- **Single machine.** These numbers come from one desktop, with the Balanced power plan, other applications open and no
  isolation. Results do not transfer to other hardware.
- **Oversubscription.** There are six cores and no SMT, so worker counts above 6 oversubscribe the CPU.
- **Two code states.** The results combine two code states, as described under Runs used. The provenance of the
  first full run is weaker: its tree was dirty, though its code was committed unchanged.
- **Stress statistics.** Stress cases use 1 warm-up and 5 single invocations. Their confidence intervals are wider, and
  they include effects that a default job would warm away. Don't compare them directly with full-profile numbers.
- **Managed allocation only.** BenchmarkDotNet's allocation figures cover managed memory only. SkiaSharp's native
  allocations are not counted, and process memory comes only from the profiler.
- **Different page counts.** Layout scenarios produce different page counts per library, and times are per document,
  not per page.
- **Default output settings.** Compression, metadata and font subsetting defaults were kept, not aligned, so output sizes
  reflect those defaults.
- **Sampled peaks.** Peak managed heap and private bytes come from samples every 100 ms (full) or 250 ms (stress), so
  short spikes can be missed. Peak working set is the OS counter.
- **Not checked:** glyph shaping beyond text extraction, PDF/A conformance, and visual differences between libraries.

## Reproduce

Run from the repository root with the .NET 10 SDK. The runner validates every case and benchmarks the passing ones, then
the profiler and the report generator run.

```powershell
dotnet restore UnlimitedPDF.Benchmarks.slnx --locked-mode
dotnet build UnlimitedPDF.Benchmarks.slnx -c Release --no-restore
dotnet test UnlimitedPDF.Benchmarks.slnx -c Release --no-build --no-restore
./scripts/run-benchmarks.ps1 -Profile all
```

To repeat only the categories that were re-run for fixture 2026.11.2:

```powershell
./scripts/run-benchmarks.ps1 -Profile all -Category 'Generation,FileOutput'
```

Each command writes `results/<run-id>-full` and `results/<run-id>-stress`, with a manifest, validation results, raw
BenchmarkDotNet exports, profiler data and `report.html`. To regenerate reports from the raw files, run
`scripts/generate-reports.ps1`. Run folders are not committed.
